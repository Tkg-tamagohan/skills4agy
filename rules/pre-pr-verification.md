# PR 作成前に実コードとの整合と境界条件を検証する

コンパイルと単体テストが通っても、コンポーネント間の境界や PR 説明との乖離がレビュー指摘の反復を招く。
PR の作成または更新の前に、実装の結合点と変更差分を点検する。

## 手順

1. 下位層へ追加した定期処理、回収処理、照合処理が、上位のランタイムやループから実際に呼ばれていることを確認する。
2. 実装完了後または PR の作成や更新の前に、常駐デーモンや非同期チャネル、DB 永続化、IPC を含む場合はスキル `systems-pre-pr-audit` を呼び出して境界条件と競合を点検する（トリアージや修正計画のみの段階では実施しない）。
3. 新規または大幅改訂の仕様書や運用手順書を含む PR では、PR 作成前にスキル `spec-cold-review` で実行可能性、権限境界、および現行実装との整合を点検する。
4. 複数モジュール変更や新規ロジック追加を含む PR では、実装文脈から離れて `git diff <base>..HEAD` を 1 回だけ逆張り精査し、テストのアサーション緩さ、リソースや子プロセスの解放漏れ、キャンセルやエラーの伝播漏れを確認する（大規模差分では読み取り専用サブエージェントへ委任可）。
5. PR の作成または更新の前に、スキル `invariant-gate`（常駐デーモンや非同期チャネル、DB 永続化、IPC を含む変更時は `--preset systems-pre-pr`、PR 内再発防止策がある場合は `pr-review-triage` で抽出したルール Markdown を `--rules` で併用）を実行し、違反候補が挙がった項目だけを実コードで二次精査する。
6. PR のタイトル、説明、変更概要に書く提供範囲やフォールバック優先順を、`git diff <base>..HEAD` の実装内容と突き合わせてから作成または更新する。
   あわせて、記載するテスト ID と検証範囲（ドライランやモックと実測の区別）を実コードのテスト関数名および実行結果と突き合わせる。
7. PR へのレビュー指摘をトリアージしたり未 Resolve スレッドへの返信と Resolve を行ったりする場合は、スキル `pr-review-triage` に従い、一次照合後の周辺境界監査は実装フェーズへ委ねる。

## 対象外

- 単一ファイルの誤字修正や書式変更のみの PR
- 新規または大幅改訂の仕様書や運用手順書を含まないドキュメントやコメントのみの更新
- 境界や手順書に触れない数行の局所修正（手順 2 から 4 を省略可）
- 実装や PR 更新を伴わないレビュー指摘のトリアージと修正計画のみのフェーズ（手順 7 のみ適用し、手順 1 から 6 の事前検証は実施しない）
