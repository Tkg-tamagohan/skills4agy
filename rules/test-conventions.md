# テストは仕様から作成し、ID を振って結果を表で報告する

テストコードを書くときは実装ではなく要件定義書や仕様書を根拠にし、テストケースには ID を振って結果を表で報告する。
実装から期待値を逆引きしたテストは、実装のバグまで正しい挙動として固定してしまうためである。

## 手順

1. 要件定義書や仕様書を根拠にテストケースを設計し、実装と文書が矛盾しているときは推測せずユーザーに確認する。
2. テストケースには対象を表す短い識別子と連番の組み合わせ（例：`AUTH-01`）で ID を振って管理する。
3. モジュール単体だけでなく、上位ランタイムからの実呼び出し結合点、および境界内の有効対象と境界外の除外対象を混在させた入力を検証対象に含める。
4. 集約欄と明細行や複数行で同じ文言が重複し得る UI や一覧出力のテストでは、コンテナ全体の部分一致で済ませず対象要素を個別に抽出して期待値と他要素非混入を検証する。
5. 非同期待機、失敗注入、削除後復元のテストでは、壁時計の `sleep` に頼らず対象状態の到達や事前条件を確定させて空パスを防ぐ（非同期ランタイム、優先度レーン、共有ロック、資源回収の具体的な同期手順はスキル `systems-pre-pr-audit` を参照する）。
6. テスト実施後はテスト項目一覧と結果を表で報告し、失敗したケースは抽出して改善案とあわせて提示する。

## 対象外

- テストコードの作成も実施も伴わない作業
