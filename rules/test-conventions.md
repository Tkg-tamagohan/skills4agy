# テストは仕様から作成し、ID を振って結果を表で報告する

テストコードを書くときは実装ではなく文書を根拠にし、テストケースには ID を振って結果を表で報告する。
実装から期待値を逆引きしたテストは、実装のバグまで正しい挙動として固定してしまう。

## 仕様や要件から作成する

- テストは実装コードの挙動をなぞるのではなく、要件定義や仕様書などの文書を根拠に作成する。
- 実装と文書が矛盾しているときは、どちらを正とするか自分で推測せず、ユーザーに確認する。
- 非同期待機や中断、失敗注入、有界チャネルのテストでは、対象条件の発火状態（`Poll::Pending` 到達や処理途中のバッチ境界など）を同期して確定させてから後続を検証し、壁時計の `sleep` 待ちによる空パスを防ぐ。
- 優先度レーン分離や複数キュー構成では、別レーンのイベントや名称から推測した件数 API を完了バリアにせず、対象レーンの処理カウンタ増分や実体確認済みの状態遷移で同期する。
- マルチスレッド非同期ランタイム上で同期ブロッキングモック（同期バリアやスリープ等）を使うテストは、ランタイム種別ガード付きの `block_in_place` 等でタイマードライバ飢餓を防ぐ。
- モジュール単体のテストだけでなく、上位ランタイム（定期タスクや IPC 入口）から実呼び出しされている結合点と本番相当の境界まで検証対象に含める。

## ID を振って結果を表で報告する

- テストケースを作成するときは、対象を表す短い識別子と連番の組み合わせ(例: `AUTH-01`)で ID を振って管理する。
- テスト実施後は、テスト項目一覧とテスト結果を表にまとめて表示する。
- 失敗したケースは追加で抽出し、改善案とあわせてユーザーに提示する。

## 対象外

- テストコードの作成も実施も伴わない作業
