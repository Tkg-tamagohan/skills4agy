# Rust アプリの安全なリリース配布と自己更新設計

Rust 製の常駐サービスやデスクトップアプリを安全に配布し、自己更新させるための設計指針と運用手順を定める。
公開順序の不備による破損リリース露出、旧鍵の性急な失効による自己更新断絶、および Windows インストーラ現場での失敗を防ぐことを目的とする。
本スキルでは必須となる抽象要件と、データ形式やスクリプト言語などの例示を明確に区別して扱う。

## 責任範囲の境界

- **GitHub Actions の汎用 CI と公開骨格**：ワークフロー骨格、権限最小化、`source_sha` 固定、言語非依存の原子的公開順序、定期脆弱性監査は `github-actions-ci` に委ねる。
  併用時は公開骨格を `github-actions-ci` が担い、署名マニフェスト対応と公開鍵整合を本スキルが担う。
- **ローカル PowerShell とシェル罠**：`run_command` での文字コード、`PSModulePath` 除去と `Microsoft.PowerShell.Security.psd1` 明示読込、および `MethodInvocationException.InnerException` 連鎖展開の基本手順は `windows-cli-pitfalls` に委ねる。
- **外部クレートのライセンス確認**：依存追加およびバージョン更新時の一次確認と義務遵守は `library-license` に委ねる。
- **シークレット登録のユーザー案内**：署名秘密鍵等の Secrets 登録依頼は `scoped-secret-provisioning` に委ねる。
- **一般手作業の手順書化**：初回鍵発行や鍵ローテーション等のリリース運用ランブックは本スキルを優先し、リリース以外の一般的な実装計画内手作業手順書化は `user-work-runbook` に委ねる。
- **日本語の文章規範**：ランブックや運用文書の執筆と `slop_lint.py` による検査は `japanese-tech-writing` に委ねる。

## 最小依存と再現ビルドの設計

サプライチェーン攻撃面とライセンス不整合を抑えるため、ビルド再現性と依存境界を初期設計で固定する。

1. すべてのビルド、クリップ検査、テストで `--locked` を強制し、`Cargo.lock` の暗黙更新を禁止する。
2. 依存追加時は `cargo metadata --format-version 1 --locked` で推移的依存を含めた全クレートのライセンスを棚卸しし、`library-license` に従って両立性を確認する。
3. 自作リスクが高い暗号検証領域（例として Ed25519 署名検証の `ed25519-dalek`）のみ最小限の外部クレートを採用し、SemVer 比較や Base64 デコードなどの小規模処理は標準ライブラリで実装する。
4. 更新マニフェストや配布物の HTTP 取得には OS ネイティブ API や最小構成のクライアントを用い、リダイレクト先のホスト制限、HTTPS スキーム限定、および応答サイズ上限を手動で検証する。
5. 脆弱性監査（`cargo audit` 等）は通常 PR の必須条件へ入れず、`github-actions-ci` に従って週次および手動の独立ワークフローへ分離する。

## 改ざん防止と鍵ライフサイクル設計

自己更新クライアントは、署名検証に失敗するあらゆる状態を拒否するフェイルクローズで設計する。

- **公開鍵リングのコンパイル時埋め込み**：配布バイナリは公開鍵リング JSON を `include_str!` でコンパイル時に埋め込み、外部の設定ファイル上書きを許さない。
  初期状態のプレースホルダ（有効な `active` 鍵が 0 件の状態）では、検証処理を必ずフェイルクローズで停止させる。
- **署名エンベロープの先行検証**：更新マニフェストの本文パースや互換性判定（最低アップデータ版数判定など）を実行する前に、まず署名エンベロープで暗号署名を検証する。
  未検証の JSON を信頼して分岐処理やバージョン比較へ進んではならない。

```json
// 署名エンベロープ形式の例示（具体のキー名は設計に合わせて調整可能）
{
  "schema_version": 1,
  "key_id": "prod-2026-11",
  "algorithm": "ed25519",
  "signature_b64": "<Base64エンコードされた64バイト署名>"
}
```

- **2 段階鍵ローテーション**：旧版バイナリはビルド時点の公開鍵リングしか持たないため、運用鍵の切り替えは必ず 2 段階で行う。
  1. 第 1 段階では、公開鍵リング上で旧鍵を `active` のまま残しつつ新鍵を `active` として追加し、秘密鍵はまだ旧鍵のまま移行版リリースを配布する。
  2. 移行版の展開後に署名秘密鍵を新鍵へ切り替え、公開鍵リングの旧鍵を `revoked` へ変更して次版を公開する。
  3. 署名検証が本文解析より先に実行されるため、旧鍵の失効後に残存した移行版未満の旧クライアントは自動誘導できず、新しい署名付きインストーラの手動配布が必要になる境界を運用手順書へ明記する。
- **検出済み更新状態のローカル永続化**：後続の適用確認や UI 表示のために更新情報をローカルへ保存する場合は、更新マニフェスト本体と署名エンベロープを対で保存する。
  起動時や再読込時にはファイルサイズ上限、署名、厳密な SemVer 昇順（`manifest.version > current_version`）、およびファイル名の安全性（パストラバーサル文字を含まないこと）を毎回再検証してフェイルクローズとする。
  リモート確認時のキャッシュ消去は対象リソースの不在（HTTP 404）が確認できた場合のみに限定し、一時障害（HTTP 503 等）やオフライン時は既存キャッシュを保持する。

## ドライランと原子的公開の運用境界

リリース公開の途中で不完全な成果物が露出しないよう、`github-actions-ci` の原子的公開順序へ署名配布物を対応づける。

1. 公開処理では `draft` リリースを作成したうえで、まずインストーラ、ZIP、チェックサム一覧（`SHA256SUMS.txt` 等）の実体成果物をアップロードする。
2. 最後に更新マニフェストと署名エンベロープをアップロードし、末尾で `--draft=false` へ切り替えて公開する。
3. `dry_run` 実行でジョブ内の一時テスト鍵を生成するときは、リポジトリの Secrets に登録された本番用鍵識別子（`*_KEY_ID` 等）が環境変数に残っていても衝突しないよう、コマンド引数でテスト専用の `--key-id` を明示指定する。
4. バイナリ本体は一時テスト鍵を生成する前のビルド工程でリポジトリ内の公開鍵リングを `include_str!` で埋め込んでいるため、コンパイル済みバイナリは一時テスト鍵を信頼しない。
   したがって、`dry_run` の検証範囲はパッケージング、一時鍵による署名、および配布物検証スクリプトの通過までであることをワークフローコメントとランブックへ明記する。

```powershell
# NG（本番用 *_KEY_ID Secret の環境変数を拾ってしまい dry_run が不整合で失敗し得る）
python scripts/build_release_artifacts.py --public-keys $tmpPub --private-key-file $tmpPriv

# OK（テスト専用 ID を明示して本番 Secrets との衝突を防ぎ、出力先も一時領域へ分離する）
python scripts/build_release_artifacts.py --public-keys $tmpPub --key-id dry-run-test --private-key-file $tmpPriv
```

## Windows パッケージングと配布物テスト

Windows 向けのインストーラ構築、ACL 保護、アップグレード時ロールバック、および配布スクリプトの Windows 上でのテスト手順を扱う場合は [references/windows-installer-packaging.md](references/windows-installer-packaging.md) を参照する。
配布物生成と検証スクリプトの単体テストは `github-actions-ci` に従い、Linux ランナーだけでなく `windows-latest` 上でも厳格警告モード（例として Python の `python -W error -m unittest`）で実行する。

## リリースランブックと検証境界の記録

リリース運用の再現性を保つため、ランブックには次の 7 章構成を備える。

1. 前提条件とバージョンを同期する対象ファイル一覧
2. 初回署名鍵の発行と CI Secrets への登録手順
3. リリース前検査（`preflight` 等）と `dry_run` の実行手順
4. 本番タグ付与、原子的公開順序、および公開後の事後確認
5. 2 段階鍵ローテーションの実行手順
6. 不具合時のパッチ前進ロールバック、鍵漏洩時の緊急失効、および導入失敗時の端末側ロールバック
7. アンインストール時のデータ保全一覧表

検証結果を記録する際は、CI で自動実行された検査、ローカルで別途実行した静的検査や単体テスト、および実機 E2E 試験を混同しない。
実公開鍵を埋め込んだバイナリによる自己更新、実インストーラの昇格とサービス再起動、実機アンインストール時のデータ保全は合成テストで代替せず、実機 E2E の確認対象として区別して残す。

## 原則

- クレート依存は `--locked` と最小構成で固定し、推移的依存のライセンスを全件確認したうえで定期的な脆弱性監査を PR から分離する。
- 公開鍵リングは `include_str!` でバイナリへ埋め込み、未設定時はフェイルクローズ、検証時は本文パースより先に署名エンベロープを検証する。
- 鍵の切り替えは必ず「両鍵 `active` で旧鍵署名の移行版配布」と「新鍵切替および旧鍵 `revoked` 化」の 2 段階で行う。
- ローカル保存した更新状態は毎回サイズ、署名、厳密 SemVer 昇順、ファイル名を再検証し、HTTP 404 以外では消去しない。
- `dry_run` ではテスト用 `--key-id` を明示して本番鍵 ID と衝突させず、埋め込み鍵バイナリとの信頼境界を明記する。
- CI 検査、ローカル別途検証、および実機 E2E 対象は分離してランブックと記録へ残す。
