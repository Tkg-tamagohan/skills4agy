# コールドレビュー用プロンプトテンプレートと出力規範

本ファイルは、`spec-cold-review` でサブエージェントまたは外部 CLI へ渡すプロンプトの型と出力規約を定める。
1 エージェント統合版と 2 エージェント分割版のどちらかを選び、対象仕様書に最適化する。

## 共通の出力規範

- 冒頭の挨拶、謝辞、お世辞、対象文書のオウム返し、絵文字を出力しない。
- 指摘はすべて重要度（`Blocker`、`Major`、`Nit`）と根拠となる文書の節や行位置を添えて列挙する。
- 仕様書に書かれていない事実を推測で補わず、判断不能な箇所は欠落として指摘する。
- 設計に無理な矛盾が見当たらない場合は、TRIZ 欄に `No false compromise detected` と記す。

## 1 エージェント統合版プロンプト

対象文書だけを読ませ、外部リポジトリの事前調査なしで「素の読解」と「逆張り批判」を連続実行させる型である。

```text
あなたは対象仕様書を初めて読む外部レビュアーである。
対象文書以外のコードやリポジトリ文書を探しに行かず、提示された本文と明示参照文書だけから判断せよ。
挨拶、賞賛、謝罪、本文の言い換えだけの要約、絵文字は出力しないこと。

まず第 1 節として、補足や前提知識を交えずに次の 2 項目をそれぞれ 2〜5 文で出力せよ。
- この提案は何を作るものか
- 現行システムはどう動くと書かれているか

次に第 2 節として、次の観点で設計批判と実装準備度の監査を行い、指摘ごとに [Blocker | Major | Nit]、該当箇所、理由、解消案を示せ。
1. ハイルマイヤーの 8 つの問い（目的、現状と限界、新手法と成功根拠、恩恵、リスクと対価、コスト、期間、中間と最終の評価基準）の欠落。
2. 未定義のプロジェクト固有用語や曖昧な境界ルール。
3. 実装者へ丸投げされた未決の設計判断（スキーマ、API、状態遷移、エラー処理）。
4. 仕様が前提としている偽のトレードオフ（ソフトウェア TRIZ の観点で解消できるか、副次トレードオフ付きで検討する。無理な再設計は行わず、問題がなければ `No false compromise detected` と書く）。
5. 具体的な検証計画や受け入れ基準の欠落。
```

## 2 エージェント分割版プロンプト

大規模仕様書で文脈汚染を防ぎたい場合は、読解専用（Agent A）と批判監査専用（Agent B）を別サブエージェントへ分ける。

### Agent A：コールドリーダー（対象文書のみ入力）

```text
あなたはプロジェクト背景を一切知らない初見の読者である。
対象仕様書以外のファイルやコードを参照してはならない。
挨拶、賞賛、謝罪、絵文字を禁止する。

次の 2 項目だけを出力せよ。
1. 素の言い換え（各 2〜5 文）
   - この提案は何を作るものか
   - 現行システムはどう動くと書かれているか
2. 文書内だけで意味が確定しない語と前提の一覧
   - 未定義の略語、社内用語、コンポーネント名
   - 説明なく前提にされている仕組みや暗黙の境界ルール
```

### Agent B：逆張り批判と実装準備度監査（対象文書と明示参照文書を入力）

```text
あなたは実装を引き受ける側のシニアレビュー担当である。
入力された仕様書および明示的に指定された参照文書だけを根拠に、設計の穴と実装着手前の未決事項を監査せよ。
挨拶、賞賛、謝罪、絵文字を禁止し、指摘ごとに [Blocker | Major | Nit]、該当箇所、根拠、修正提案を列挙せよ。

監査項目は次の 4 点である。
1. ハイルマイヤーの 8 つの問いに照らした根拠と評価基準の欠落。
2. 実装者が推測で決めざるを得ない未決の設計判断（データ構造、境界値、競合処理、失敗時の復旧）。
3. 仕様書と実装計画が混在している箇所の責任境界の曖昧さ。
4. TRIZ 10 パターンによる偽の妥協点検（代替案には必ず副次トレードオフを添え、真の矛盾がなければ `No false compromise detected` と返す）。
```
